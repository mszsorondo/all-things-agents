IDEAL Process Model

Process overview and purpose
- Purpose: Standardize and control the hiring process to minimize rework, ensure compliance, and improve candidate experience while retaining necessary assessment depth.
- Design principle: Preserve legitimate behaviors from the AS-IS (e.g., optional early telephonic triage, track-specific interviews, background screening with possible escalation) while removing wasteful loops, enforcing proper sequencing, and clarifying end states.

Key stakeholders and roles involved
- Roles are not explicitly specified in the source. Responsibilities inferred from activity names only:
  - Recruiting/Screening staff: Telephonic Screening, Screening Interview, Make Job Offer, recording Application Rejected.
  - Technical interviewers: Coding Interview, Frontend Interview, Backend Interview, ML Interview.
  - Compliance/Background-check function: Background Check, Extensive Background Check.

Detailed step-by-step process flow
1) Start conditions and triggers
   - Trigger: Hand In Job Application (start event).
   - Case record is created; candidate track is determined by requisition (Frontend, Backend, or ML).

2) Initial triage and screening (controlled optionality)
   - Telephonic Screening (optional, inclusive decision)
     - Performed if initial application requires clarification or basic qualification check.
     - Decision (exclusive):
       - Fail → Application Rejected → End.
       - Pass or Not Needed → proceed.
   - Screening Interview (mandatory)
     - Structured screening to confirm role fit.
     - Decision (exclusive):
       - Fail → Application Rejected → End.
       - Pass → proceed.

3) Technical assessment (track-based, enforced sequencing)
   - Coding Interview (mandatory for all technical tracks)
     - Decision (exclusive):
       - Fail → Application Rejected → End.
       - Pass → proceed to track-specific interview.
   - Track-specific interview (exclusive choice by track)
     - Frontend Interview OR Backend Interview OR ML Interview (choose exactly one per requisition).
     - Decision (exclusive):
       - Fail → Application Rejected → End.
       - Pass → proceed.
   - Behavioral Interview (mandatory, once)
     - Decision (exclusive):
       - Fail → Application Rejected → End.
       - Pass → proceed.

   Notes on rework control:
   - At most one additional Coding Interview is allowed for calibration in edge cases; additional repeats are disallowed.
   - Track-specific interview may be repeated once only if there is a scheduling/assessment defect; cross-track mixing (e.g., both Frontend and Backend in one case) is disallowed unless the requisition genuinely covers multiple tracks (requires prior role clarification before interviews).

4) Background screening (compliance-gated)
   - Background Check (standard)
     - Decision (exclusive):
       - Clean → proceed.
       - Issues found → escalate.
   - Extensive Background Check (conditional escalation)
     - Performed only when the standard Background Check flags issues.
     - Decision (exclusive):
       - Pass → proceed.
       - Fail → Application Rejected → End.

   Control rule:
   - Background Check and Extensive Background Check are mutually exclusive unless escalation occurs (no parallel or redundant checks).

5) Offer decision and issuance (properly gated)

   - Outcomes:
     - All required steps passed → Make Job Offer.

6) Parallel activities and synchronization points

7) Exception handling and escalation procedures

   - Early exit:

8) End conditions and outcomes
   - Application Rejected (visible, terminal).
   - Make Job Offer (visible, terminal).
   - No implicit endings: silent/τ-based closures are eliminated; every case ends with an explicit terminal event.

Process metrics and performance characteristics
- Reduced variability and rework:
  - Sequencing constraints remove unnecessary loops and cross-track mixes.
  - Caps on re-interviews reduce cycle time and interviewer load.
- Compliance improvement:
