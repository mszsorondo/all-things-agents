Business Process Description:
AS-IS Process Model

Process overview and purpose
- This AS-IS model describes the observed hiring/recruitment selection process derived from the provided Petri net, DFG and variant data. The process begins when a candidate hands in a job application and ends when the case reaches a terminal outcome: Application Rejected or Make Job Offer. The observed behavior contains multiple interleaved and looping interview tracks (telephonic screening, screening interview, coding interview, frontend/backend/ML interviews, behavioral interview), two levels of background checks (Background Check and Extensive Background Check), and frequent nonstandard transitions (e.g., rejected cases subsequently re-entering interviewing steps or being offered jobs). The purpose of documenting the AS-IS model is to make explicit the actual control-flow, including rework, data-quality issues, and performance bottlenecks revealed by direct-follows counts and discovered Petri net structure.

Key stakeholders and roles involved (inferred)
- Candidate (initiates the process)
- Recruiter / HR (schedules telephonic screening, background checks, issues offers)
- Screening/Technical Interviewers (conduct screening, coding, frontend, backend, ML interviews)
- Behavioral Interviewers / Hiring Manager (conduct behavioral interview and final evaluation)
- Background-check vendor or HR function (performs Background Check and Extensive Background Check)

Detailed step-by-step process flow
Start conditions and triggers
1. Start: candidate hands in a job application. Observed initial splits: some applications are immediately rejected (Hand In Job Application -> Application Rejected), while the majority proceed to Telephonic Screening.
   - Observed counts: Hand In -> Telephonic Screening = 8,799 cases; Hand In -> Application Rejected (direct) = 1,201 cases. (Interpretation: ~12% of candidates rejected immediately.)

Main flow and branching structure
2. Telephonic Screening (phone screening)
   - After telephonic screening applicants follow three main observed branches (distribution from Telephonic Screening, frequency basis):
     a) Telephonic -> Background Check: 3,961 cases (~45% of those screened)
     b) Telephonic -> Screening Interview: 3,848 cases (~44% of those screened)
     c) Telephonic -> Application Rejected: 990 cases (~11% of those screened)
   - Telephonic screening is therefore a major gating activity with a three-way exclusive split in practice.

3. Screening Interview and the Screening <-> Background relationship
   - Screening Interview receives candidates both directly from Telephonic Screening (3,848) and from Background Check (3,961), for a combined observed inflow of ~7,809 cases.
   - Observed transitions out of Screening Interview include:
     - Screening -> Background Check: 3,961 (many candidates are moved to background check after screening)
     - Screening -> Coding Interview: 1,517
     - Screening -> Extensive Background Check: 1,055
     - Screening -> Application Rejected: 1,389
   - There are cycles between Screening Interview and Background Check in both directions; data shows Screening -> Background and Background -> Screening both at the same frequency (3,961), indicating an alternating pattern for many cases.

4. Background Checks (two levels)
   - Background Check (standard) is frequently executed: Telephonic -> Background Check = 3,961 and Screening -> Background Check = 3,961; Background Check -> Coding Interview = 1,413; Background Check -> Extensive Background Check = 1,044; Background Check -> Application Rejected = 1,391.
   - Extensive Background Check is used in a subset of cases. Observed transitions: Extensive Background Check -> Application Rejected = 1,125; Extensive Background Check -> Coding Interview = 974. Extensive Background Check often follows Screening or Background (both around 1,055 / 1,044 respectively).
   - The sequence indicates substantial switching between screening and background-check activities, and that background checks sometimes occur before technical interviews, sometimes after.

5. Technical interview track (Coding -> Frontend/Backend/ML, etc.)
   - Screening Interview -> Coding Interview (1,517). Coding Interview then flows to:
     - Coding -> Frontend Interview: 1,513
     - Coding -> Backend Interview: 701
     - Coding -> ML Interview: 1,304
     - Coding -> Application Rejected: 386
   - There are observed chains and loops among Frontend, Backend and ML interviews:
     - Coding -> Frontend (1,513) then Frontend -> ML (878) and Frontend -> Backend (529) and Frontend -> Behavioral (853); Frontend -> Application Rejected (653)
     - ML -> Frontend (913) and ML -> Behavioral (754) and ML -> Application Rejected (546)
     - Backend -> Frontend (487) and Backend -> Behavioral (417) and Backend -> Application Rejected (295) and Backend -> ML (152)
   - The Petri net indicates a parallel split for technical interviews (tauSplit_9 -> ML, Backend, Frontend). The DFG shows frequent interleaving and bidirectional sequences among these technical nodes, meaning candidates commonly experience multiple technical interviews, sometimes in different orders. Technical interviews are not strictly sequential; they may run in parallel or be revisited.

6. Behavioral Interview and finalization
   - After technical interviews, many candidates proceed to the Behavioral Interview: observed transitions Frontend -> Behavioral (853), ML -> Behavioral (754), Backend -> Behavioral (417). Behavioral Interview -> Make Job Offer = 1,850 (strong path to offer), but Behavioral Interview also shows a self-loop (Behavioral -> Behavioral = 1,032), indicating repeated behavioral rounds for many candidates.
   - Make Job Offer also shows a self-loop (Make Job Offer -> Make Job Offer = 861) and an anomalous backwards edge Make Job Offer -> Application Rejected (110), and Application Rejected -> Make Job Offer (690) indicating inconsistent terminal-state handling in the event log.

7. Application Rejected behavior
   - Application Rejected appears often as a terminal outcome: many standard reject transitions (e.g., Screening->Application Rejected 1,389; Background Check->Application Rejected 1,391; Extensive Background Check->Application Rejected 1,125; Coding->Application Rejected 386; Telephonic->Application Rejected 990; Hand In -> Application Rejected 1,201).
   - However, there are nonstandard transitions where Application Rejected is followed by another interviewing step or even Make Job Offer (Application Rejected -> Behavioral Interview = 740; Application Rejected -> Make Job Offer = 690; Application Rejected -> Application Rejected = 654). These indicate either data-quality problems, process instabilities (re-opened candidate files), or parallel logging artifacts (events from different re-opened attempts recorded under same case id).

Decision points with criteria and observed outcomes (in practice)
- After Hand In: quick reject (direct Application Rejected) vs. proceed to Telephonic Screening. Criteria observed (not explicit in log) likely resume quality or hard-gate mismatch.
- Telephonic Screening: three-way decision: send to Screening Interview, send to Background Check, or reject. Criteria: fit for role, minimum technical qualification, or obvious mismatch.
- After Screening Interview: route to Coding Interview, request Background Check / Extensive Background Check, or reject.
- After Background Check: either pass (to Coding Interview) or fail (to Application Rejected) or escalate (to Extensive Background Check).
- After Coding and technical interviews: either continue to further technical rounds (Frontend/Backend/ML), go to Behavioral Interview, or reject.
- At Behavioral Interview: often leads to Make Job Offer or additional behavioral rounds.
- Terminal decisions: Make Job Offer and Application Rejected are the observed end outcomes, but the log shows that those states are not strictly terminal.

Parallel activities and synchronization points
- Petri net evidence and DFG indicate parallel technical interviews (Frontend/Backend/ML) are often executed in parallel or in any order (tauSplit_9). Synchronization occurs before final decisions (e.g., tokens join via tauJoin constructs). The net also shows structural invisible (tau) splits/joins that allow skipping of activities via skip_* transitions.

Exception handling, rework loops, and anomalous behavior
- Rework and repetition: Behavioral Interview repeated often (self-loop); Make Job Offer repeats; technical interviews revisited (loops among Frontend/Backend/ML); Screening and Background Check alternate frequently.
- Nonterminal rejects and offers: Observed Application Rejected -> Behavioral Interview and Application Rejected -> Make Job Offer paths show that cases labeled as rejected sometimes continue and even result in offers.
- Skipped activities: The discovered net contains many skip and init_loop invisible transitions: skip_* transitions route flow around tasks (model captures optional activities). This matches variant data where many variants omit certain tasks (e.g., some traces go Hand In -> Telephonic -> Application Rejected without further interviews).

End conditions and observed outcomes
- Terminal outcomes in the AS-IS logs: Application Rejected and Make Job Offer. The Petri net final marking is reached via a sink place connected through tauJoin_15 and other invisible joins; in practice the two distinct business outcomes are rejection or offer. However, many traces show inconsistent transitions between these outcomes.

Key challenges and pain points (AS-IS)
- Complex, non-deterministic control-flow: many loops, skip/tau transitions, and parallel interleavings (technical interviews) make the process hard to reason about and hard to measure.
- Rework and wasted effort: extensive back-and-forth between Screening and Background, and repeated behavioral rounds, indicate inefficiencies and candidate friction.
- Nonterminal terminal states: Application Rejected and Make Job Offer appear as non-final in the log (cases re-enter later steps), signaling case re-openings, logging errors, or process inconsistencies.
- Data-quality / logging inconsistencies: transitions like Application Rejected -> Make Job Offer (690 cases), and Make Job Offer -> Application Rejected (110) are business-incoherent and point to event-classification problems or merged case-IDs.
- Long lead times for critical transitions: Extensive Background Check and some candidate routing paths show very large mean times, indicating vendor delays or long asynchronous waits.
- High variability: candidate routing has many low-frequency but long variants where candidates traverse many technical rounds before an outcome; this generates high variance in cycle time and resource usage.
- Lack of clear gating rules: while telephonic screening acts like a gate, the observed mixing of background checks (before/after technical interviews) shows inconsistent gating policy.
- Potential compliance risk: Extensive Background Check escalations and inconsistent handling of rejections/offers can produce legal or data-privacy complications if checks are re-run arbitrarily.

Concluding observations (AS-IS)
- The observed hiring process is highly flexible but noisy: flexibility comes with high rework, cycle-time variance, and data-quality problems.
- Any improvement program should address: (1) standardize gating logic (screening -> technical -> behavioral -> decision), (2) treat Application Rejected / Make Job Offer as strict terminal states, (3) rationalize background checks to avoid unnecessary work and long vendor waits, (4) limit rework loops with defined retry policies, and (5) fix logging/case-ID issues to avoid state contradictions.
