=== DECLARE INTERPRETATION GUIDE ===

DECLARE is a declarative process modeling language based on temporal logic constraints.

OUTPUT FORMAT:
--------------
The output starts with constraint explanations, then lists discovered constraints:
"I have a DECLARE declarative process model containing the following constraints:
Existence: the activity is executed at least once.
Absence: the activity is not executed.
Exactly 1: the activity is executed exactly one time.
Initialization: the trace starts with one of the given activities.
Responded existence: given (A, B), if A occurs then B also occurs.
Co-Existence: given (A, B), if A occurs then B also occurs.
Response: given (A, B), if A occurs then B also occurs in the future.
Precedence: given (A, B), if B occurs then A occurs in the past.
Succession: both response and precedence are satisfied.
...

These are the constraints of the model:
Existence: Activity1, Activity2, ...
Responded Existence: ('A', 'B'), ('C', 'D'), ...
Response: ('A', 'B'), ...
Initialization: Activity1
Exactly 1: Activity1, Activity2, ..."

CONSTRAINT CATEGORIES:

EXISTENCE CONSTRAINTS:
- Existence: Activity must occur at least once
- Absence: Activity must not occur
- Exactly 1: Activity occurs exactly once
- Initialization: Trace must start with this activity

RELATION CONSTRAINTS:
- Responded Existence: If A occurs, B must occur (anywhere)
- Co-Existence: A and B always occur together or both absent
- Response: If A occurs, B must occur afterwards
- Precedence: B can only occur if A occurred before
- Succession: Both response and precedence

CHAIN CONSTRAINTS (immediate succession):
- Chain Response: B must immediately follow A
- Chain Precedence: A must immediately precede B
- Chain Succession: Both chain response and precedence

NEGATIVE CONSTRAINTS:
- Non Co-Existence: A and B cannot both occur
- Non Succession: B cannot follow A
- Non Chain Succession: B cannot immediately follow A

PHILOSOPHY:
- "Everything not forbidden is allowed"
- Specifies constraints that must hold
- Any execution path satisfying constraints is valid

USE FOR:
- Knowledge-intensive processes
- Compliance requirements
- Flexible workflow modeling
- Understanding what MUST happen vs what CAN happen
