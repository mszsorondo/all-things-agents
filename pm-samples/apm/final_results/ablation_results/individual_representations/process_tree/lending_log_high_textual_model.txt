IDEAL Process Model

Process overview and purpose
- Purpose: Provide a clean, controlled, and consistent loan intake and decisioning process that eliminates contradictory outcomes, enforces proper sequencing, and bounds rework while retaining all valid business outcomes seen in the source (pre-screen rejection, final denial, and signing).
- This IDEAL model streamlines the AS-IS by:
  - Making underwriting submission mandatory before any signing.
  - Ensuring final outcomes (“Loan Denied” vs. “Sign Loan Agreement”) are mutually exclusive and occur in the correct order.
  - Replacing the explicit 'skipped_examination' activity with a governed decision to include or omit preparatory checks based on documented criteria (no new tasks are added; the gateway controls existing optional activities).
  - Keeping optional due-diligence tasks but clarifying when they are used and bounding loops.

Key stakeholders and roles involved
- Applicant/Borrower: initiates appointment, submits application, signs the agreement.
- Internal processing staff (generic): set appointment, verify borrower information, conduct or arrange due-diligence tasks.
- Underwriting (recipient role implied by “Submit File to Underwriter”): receives the case and produces an outcome realized by either “Loan Denied” or “Sign Loan Agreement.”

Detailed step-by-step process flow
Start conditions and triggers
- Start event: Applicant performs “Request Appointment.”

Main flow
1) Request Appointment (start)

2) Exclusive decision: Appointment outcome
   - Appointment Denied (end), or
   - Proceed with appointment setup and intake.

3) Intake and verification
   - Set Appointment
   - Hand In Credit Appliaction
   - Verify Borrowers Information

4) Exclusive decision: Pre-screen outcome
   - Application Rejected (end), or
   - Proceed to due diligence and underwriting preparation.

5) Due diligence (governed optionality, no explicit 'skipped_examination' activity)
   - Conditional, policy-driven inclusion of existing optional checks:
     • Request Co-Signer On Loan (optional; only when risk rules indicate).
     • Make Visit to Assess Colatteral (optional, repeat as needed up to a defined maximum or until sufficient evidence is gathered; the loop is bounded by policy to prevent uncontrolled rework).
   - If none of the above is required by policy, the case proceeds directly to submission (the gateway replaces the explicit 'skipped_examination' event).

6) Submit File to Underwriter (mandatory)
   - All cases that reach this stage must be submitted before any final outcome.

7) Underwriting outcome (exclusive decision; realized by existing outcome events)
   - Loan Denied (end), or
   - Sign Loan Agreement (end).
   - These outcomes are mutually exclusive and occur only after submission to underwriting; parallel logging with other outcomes is not permitted.

Parallel activities and synchronization points
- Parallelism is removed around the denial/signing stage to prevent conflicting states.
- Optional due-diligence tasks (co-signer request and collateral visits) may run in parallel with each other before submission, when both are required, but they must complete (or be skipped by policy) before “Submit File to Underwriter.” Synchronization occurs at submission.

Exception handling and error paths
- If due-diligence attempts fail (e.g., collateral remains insufficient or no acceptable co-signer is available within policy bounds), the case proceeds to underwriting submission with current evidence; underwriting may then lead to “Loan Denied.”
- Early termination routes remain:
  - Appointment Denied (pre-intake).
  - Application Rejected (post-verification).

Rework loops and escalation procedures
- Rework is limited to a bounded number of “Make Visit to Assess Colatteral” iterations as defined by policy. Exit occurs upon sufficient evidence or reaching the cap.
- No signing occurs until after “Submit File to Underwriter” and the exclusive underwriting outcome gateway.
- Escalations (if organizationally defined) would occur outside the scope of these named activities; the IDEAL control flow does not introduce new activities.

End conditions and outcomes
- Appointment Denied (early end).
- Application Rejected (early end).
- Loan Denied (final end after underwriting).
- Sign Loan Agreement (final end after underwriting).
- No case ends with both a denial and a signature.

Process metrics and performance characteristics (targets and controls)
- Conformance targets:
  - 100% of signed cases have “Submit File to Underwriter” completed beforehand.
  - 0% cases with both “Loan Denied” and “Sign Loan Agreement.”
  - 0% usage of explicit 'skipped_examination' activity (replaced by governed gateway logic).
- Efficiency/quality metrics:
  - Average and percentile cycle times from “Request Appointment” to each terminal outcome.
  - Pre-screen fallout rates: “Appointment Denied” and “Application Rejected.”
  - Due-diligence utilization rates: percentage with “Request Co-Signer On Loan,” distribution of collateral visit counts, and bounded rework compliance.
  - Underwriter submission rate: 100% for all cases that pass pre-screen.

- Control metrics:
  - SLA adherence for completion of due-diligence tasks before submission.
  - Exceptions where due-diligence required by policy was skipped (should be 0 with proper governance).

Improvements made relative to AS-IS
- Removed contradictory parallel denial/signing behavior; outcomes are exclusive and sequenced post-underwriting.
- Enforced mandatory “Submit File to Underwriter” before any signing.
- Replaced the explicit 'skipped_examination' event with policy-driven gatewaying (no new tasks added), ensuring traceable rationale without logging a “skip” activity as the sole action.

- Preserved all legitimate outcomes present in the source (pre-screen rejection, final denial, signing) while eliminating noncompliant or ambiguous paths.
