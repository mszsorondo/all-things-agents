=== PETRI NET INTERPRETATION GUIDE ===
A Petri net is a mathematical model for distributed systems consisting of:

1. PLACES (circles): Represent states or conditions in the process
   - Initial marking: Places with tokens at the start (process entry points)
   - Final marking: Places with tokens at the end (process exit points)
   - Empty places: Intermediate states

2. TRANSITIONS (rectangles): Represent activities or events
   - Labeled transitions: Visible activities (e.g., "Submit Application")
   - Silent/tau transitions: Internal logic without visible activity
   - Parallel transitions: Can fire simultaneously (concurrent activities)

3. ARCS (arrows): Connect places and transitions
   - Place→Transition: Precondition (transition needs token in place to fire)
   - Transition→Place: Postcondition (transition produces token in place)
   - Arc weight: Number of tokens consumed/produced

4. BEHAVIORAL SEMANTICS:
   - A transition is ENABLED when all input places contain tokens
   - Firing consumes tokens from input places, produces in output places
   - Multiple tokens in a place indicate multiple process instances
   - Deadlocks occur when no transition can fire
   - Loops indicate repetitive behavior

5. INDUCTIVE MINER SPECIFICS:
   - Guarantees sound workflow nets (proper completion)
   - May introduce silent transitions for control flow
   - Handles noise and incomplete behavior in logs

=== BPMN INTERPRETATION GUIDE ===
Business Process Model and Notation (BPMN) is a graphical notation for business processes:

1. EVENTS:
   - Start Event (thin circle): Process initiation point
   - End Event (thick circle): Process termination point
   - Intermediate Events (double circle): Events during execution

2. ACTIVITIES:
   - Task (rounded rectangle): Atomic unit of work
   - Sub-process (rounded rectangle with +): Compound activity
   - Call Activity (thick border): Reference to another process

3. GATEWAYS (diamonds):
   - Exclusive (X or empty): XOR logic - one path only
   - Parallel (+): AND logic - all paths simultaneously
   - Inclusive (O): OR logic - one or more paths
   - Event-based (pentagon inside): Wait for events

4. FLOWS:
   - Sequence Flow (solid arrow): Order of execution
   - Default Flow (slash mark): Taken when no other condition is true
   - Conditional Flow (mini diamond): Has a condition expression

5. INDUCTIVE MINER BPMN SPECIFICS:
   - May contain process trees encoded as nested sub-processes
   - Silent transitions become empty gateways
   - Guarantees proper block structure
   - Loop structures are explicit with backward flows

6. SWIMLANES (if present):
   - Pools: Different organizations/systems
   - Lanes: Different roles within organization

READING THE XML:
- <bpmn:task id="..." name="...">: Activities to perform
- <bpmn:sequenceFlow sourceRef="..." targetRef="...">: Connections
- <bpmn:exclusiveGateway>: Decision points
- <bpmn:parallelGateway>: Concurrent execution points

=== DIRECTLY-FOLLOWS GRAPH (DFG) INTERPRETATION GUIDE ===
A DFG shows the frequency of direct succession between activities:

1. NODES: Represent activities/events in the process
   - Size often indicates frequency of occurrence
   - Color may indicate performance metrics

2. EDGES: Show direct succession relationships
   - Edge labels: Frequency of A→B succession
   - Thicker edges: More frequent paths
   - Edge absence: Activities never directly follow each other

3. START/END ACTIVITIES:
   - Start activities: First activities in traces
   - End activities: Last activities in traces
   - Multiple starts/ends indicate process variants

4. INTERPRETATION PATTERNS:
   - High-frequency edges: Main process flow
   - Low-frequency edges: Exceptions or rare variants
   - Self-loops: Activity repetition
   - Disconnected components: Independent sub-processes

5. LLM ABSTRACTION (if applied):
   - Simplifies complex DFGs to essential flows
   - Removes noise and infrequent paths
   - Groups similar activities
   - Highlights main process variants

6. LIMITATIONS:
   - Cannot distinguish XOR from AND gateways
   - May show impossible paths (not all A→B→C means A→C exists)
   - Sensitive to noise in event logs

USE FOR:
- Quick process overview
- Identifying bottlenecks (high-frequency edges)
- Finding process variants
- Detecting loops and rework

REPRESENTATION 4: PROCESS_TREE

=== PROCESS TREE INTERPRETATION GUIDE ===
A Process Tree is a hierarchical representation of process behavior:

1. OPERATORS (internal nodes):
   - → (sequence): Execute children in order
   - X (exclusive choice): Execute one child
   - + (parallel): Execute all children concurrently
   - ↺ (loop): Repeat body, execute exit condition
   - τ (silent): Hidden/internal activity

2. LEAVES:
   - Activity names: Actual process activities
   - τ: Silent/skip activity

3. SEMANTICS:
   - Read tree top-down, left-to-right
   - Each operator defines control flow for children
   - Guarantees soundness (proper completion)
   - Block-structured (properly nested)

4. EXAMPLE INTERPRETATIONS:
   - →(A, X(B, C), D): Do A, then either B or C, then D
   - +(A, B, C): Do A, B, C in parallel
   - ↺(A, B): Do A repeatedly, exit with B
   - X(→(A, B), →(C, D)): Either do A then B, or C then D

5. INDUCTIVE MINER PROPERTIES:
   - Always produces sound models
   - Handles incomplete logs
   - May introduce τ transitions for fitness
   - Rediscovers original tree if log is complete

        ============================================================================
        ABSTRACT VARIANTS INTERPRETATION GUIDE
        ============================================================================
        
        The abstract variants representation shows simplified process execution patterns
        with their frequency and performance metrics.
        
        FORMAT STRUCTURE:
        -----------------
        Each line represents one variant pattern in the format:
        
        [Header] Activity1 -> Activity2 -> ... -> ActivityN: [Metrics]
        
        COMPONENTS:
        -----------
        1. HEADER (if response_header=True):
        - Shows variant rank or identifier
        - Example: "Variant 1:" or "1."
        
        2. ACTIVITY SEQUENCE:
        - Activities separated by " -> " arrows
        - Represents the order of execution
        - Example: "Register -> Analyze -> Decide -> Reject"
        
        3. METRICS (after the colon):
        
        a) FREQUENCY METRICS:
            - Absolute: Number in parentheses, e.g., "(42)"
                Meaning: This variant occurred 42 times
            
            - Relative: Percentage value, e.g., "15.3%"
                Meaning: This variant represents 15.3% of all cases
        
        b) PERFORMANCE METRICS (if include_performance=True):
            - Format: [aggregation_method: value unit]
            - Common aggregations:
                • mean: Average duration
                • median: Middle value (50th percentile)
                • min: Fastest execution
                • max: Slowest execution
                • stdev: Standard deviation (variability)
            
            - Time units vary by scale:
                • seconds, minutes, hours, days
            
            - Example: "mean: 3.5 days, stdev: 1.2 days"
        
        READING EXAMPLES:
        -----------------
        Example 1 (Simple):
        "A -> B -> C: (150) 25.5%"
        → Pattern A→B→C occurred 150 times, representing 25.5% of all cases
        
        Example 2 (With Performance):
        "Register -> Check -> Approve: (89) 18.2%, mean: 2.3 hours, max: 8.1 hours"
        → This pattern occurred 89 times (18.2% of cases)
        → On average takes 2.3 hours, longest instance took 8.1 hours
        
        Example 3 (With Secondary Aggregation):
        "Start -> Process -> End: (200) 40%, mean: 1.5 days (median: 1.2 days)"
        → Main metric is mean (1.5 days), secondary metric is median (1.2 days)
        → If median < mean, indicates positive skew (some very long cases)
        
        INTERPRETATION TIPS:
        --------------------
        • HIGH FREQUENCY (>20%): Main process flow, optimize for efficiency
        • MEDIUM FREQUENCY (5-20%): Common variations, monitor regularly  
        • LOW FREQUENCY (<5%): Exceptions or edge cases, check if needed
        • HIGH VARIABILITY (stdev > 50% of mean): Unstable process, investigate
        • OUTLIERS (max >> mean): Bottlenecks or problems in specific cases
        
        ACTIVITY/CASE IDENTIFIERS:
        --------------------------
        • activity_key: Specifies which column represents activities
        • case_id_key: Specifies which column identifies cases
        • timestamp_key: Specifies which column contains timestamps
        
        These determine how activities and cases are extracted from your data.

=== PETRI NET (ALPHA MINER) INTERPRETATION GUIDE ===

The Alpha Miner is the foundational process discovery algorithm that constructs Petri nets based on ordering relations in the event log.

1. ORDERING RELATIONS USED:
   - Direct succession (>): Activity A directly followed by B in some trace
   - Causality (->): A causes B (A > B and not B > A)
   - Parallelism (||): A and B can occur in any order (A > B and B > A)
   - Choice (#): A and B never directly follow each other

2. CONSTRUCTION ALGORITHM:
   - Identifies start activities (first in traces)
   - Identifies end activities (last in traces)
   - Discovers causal relationships between activities
   - Creates places for each maximal set of causally related activities
   - Connects places and transitions via arcs

3. STRENGTHS:
   - Simple and interpretable algorithm
   - Produces sound workflow nets when log is complete
   - Good for discovering well-structured processes
   - Fast execution time

4. LIMITATIONS:
   - Cannot handle loops of length 1 (self-loops)
   - Cannot handle loops of length 2 (A->B->A)
   - Sensitive to noise in event logs
   - May produce disconnected or incorrect nets for complex logs
   - Assumes complete event logs

5. INTERPRETING ALPHA MINER OUTPUT:
   - Each visible transition corresponds to an activity
   - Places represent the "state" between activities
   - XOR-splits: One place with multiple output transitions
   - AND-splits: One transition with multiple output places
   - Implicit places may be missing (not all dependencies captured)

6. WHEN TO USE:
   - Educational purposes to understand process mining basics
   - Simple, well-structured processes without noise
   - When you need fast initial discovery
   - Logs with clear sequential and parallel patterns

7. COMPARISON WITH INDUCTIVE MINER:
   - Alpha: Directly from ordering relations, may produce unsound nets
   - Inductive: Block-structured decomposition, always sound
   - Alpha is simpler but less robust to real-world logs

REPRESENTATION 7: PETRI_NET_HEURISTICS
============================================================

=== PETRI NET (HEURISTICS MINER) INTERPRETATION GUIDE ===

The Heuristics Miner produces Petri nets by using frequency-based dependency measures, making it more robust to noise than the Alpha Miner.

1. DEPENDENCY MEASURE CALCULATION:
   - For activities A and B: dependency(A,B) = (|A>B| - |B>A|) / (|A>B| + |B>A| + 1)
   - Range: -1 to +1
   - Positive values: A likely causes B
   - Negative values: B likely causes A
   - Near zero: No clear dependency

2. THRESHOLDS AND PARAMETERS:
   - Dependency threshold: Minimum dependency value to include an edge
   - Positive observations: Minimum times A->B must occur
   - Relative-to-best threshold: For detecting AND/XOR patterns
   - Long-distance dependencies: Detect non-adjacent causal relationships

3. ADVANTAGES OVER ALPHA MINER:
   - Handles noise by using thresholds
   - Can detect loops of length 1 and 2
   - Identifies long-distance dependencies
   - Produces cleaner models for noisy logs
   - Distinguishes between AND and XOR splits/joins

4. PETRI NET CONSTRUCTION:
   - Activities become transitions
   - Dependency edges become arcs through intermediate places
   - AND/XOR semantics determined by frequency patterns
   - Silent transitions may be added for routing

5. INTERPRETING THE OUTPUT:
   - Strong edges (high dependency): Main process flow
   - Weak edges (low dependency): Exceptional paths
   - Self-loops: Activity repetition
   - Long-distance arcs: Skip patterns or escalations

6. SPLIT/JOIN DETECTION:
   - AND-split: All outputs typically activated together
   - XOR-split: Exactly one output typically activated
   - Based on co-occurrence frequencies in the log

7. WHEN TO USE:
   - Real-world event logs with noise
   - When you need to filter out infrequent behavior
   - Complex processes with loops
   - When Alpha Miner produces poor results

8. LIMITATIONS:
   - May over-simplify if thresholds are too high
   - May include noise if thresholds are too low
   - Parameter tuning can be challenging
   - Does not guarantee soundness like Inductive Miner

=== PETRI NET (ILP MINER) INTERPRETATION GUIDE ===

The ILP (Integer Linear Programming) Miner constructs Petri nets that perfectly fit the observed behavior by solving an optimization problem.

1. CORE CONCEPT:
   - Formulates process discovery as a mathematical optimization problem
   - Uses Integer Linear Programming to find a Petri net
   - Guarantees the net can replay ALL observed traces perfectly
   - Produces the simplest net that fits the log (minimal places/arcs)

2. OPTIMIZATION OBJECTIVE:
   - Minimize structural complexity (number of places and arcs)
   - Subject to: All traces in the log must be replayable
   - Each transition firing must respect token flow constraints

3. CONSTRAINTS:
   - Token flow conservation at each step
   - Initial marking enables first activities
   - Final marking reached after last activities
   - Non-negative token counts throughout execution

4. ADVANTAGES:
   - Perfect fitness by construction (all traces replay)
   - Finds minimal structure that explains behavior
   - Mathematically rigorous approach
   - No heuristic parameters to tune

5. LIMITATIONS:
   - Computationally expensive for large logs
   - May overfit to observed behavior (poor generalization)
   - Does not handle noise well
   - May produce complex nets for simple processes
   - Scalability issues with many activities/traces

6. INTERPRETING ILP OUTPUT:
   - Every place and arc has a purpose for some trace
   - No redundant structure (minimal representation)
   - May have many places connecting same activities
   - Complex routing structures for varied behavior

7. COMPARISON WITH OTHER MINERS:
   - vs Alpha: ILP handles more patterns but slower
   - vs Heuristics: ILP is exact, Heuristics approximates
   - vs Inductive: ILP optimizes fit, Inductive guarantees soundness

8. WHEN TO USE:
   - Small to medium-sized event logs
   - When perfect fitness is required
   - Clean logs without noise
   - Understanding exact behavioral boundaries
   - Academic/research contexts

9. READING THE NET:
   - Dense connectivity: Many behavioral variants
   - Simple structure: Regular process behavior
   - Many silent transitions: Complex control flow patterns

=== LOG SKELETON INTERPRETATION GUIDE ===

A Log Skeleton is a declarative process model that captures behavioral constraints observed in an event log.

1. CORE CONCEPT:
   - Describes WHAT constraints must hold, not HOW to execute
   - Based on activity occurrence and ordering relationships
   - Captures necessary conditions for valid traces

2. CONSTRAINT TYPES:

   a) EQUIVALENCE:
      - Activities that always occur together (same number of times)
      - If A occurs n times, B also occurs n times
      - Example: "Create Order" EQUIV "Send Invoice"

   b) ALWAYS BEFORE:
      - Activity A must occur before B (if B occurs)
      - A is a prerequisite for B
      - Example: "Receive Application" ALWAYS_BEFORE "Process Application"

   c) ALWAYS AFTER:
      - Activity B must occur after A (if A occurs)
      - B is a consequence of A
      - Example: "Submit" ALWAYS_AFTER "Fill Form"

   d) NEVER TOGETHER:
      - Activities A and B never co-occur in same trace
      - Mutually exclusive activities
      - Example: "Approve" NEVER_TOGETHER "Reject"

   e) DIRECTLY FOLLOWS:
      - B immediately follows A (no activities between)
      - Strict sequential constraint
      - Example: "Enter PIN" DIRECTLY_FOLLOWS "Insert Card"

   f) ACTIVITY OCCURRENCES:
      - Bounds on how many times an activity can occur
      - Format: activity: {min, max} or {exact_count}
      - Example: "Validate": {1, 3} means 1 to 3 times

3. READING LOG SKELETON OUTPUT:
   - Each constraint type listed separately
   - Activities mentioned by name
   - Confidence/support values may be included

4. CONFORMANCE CHECKING:
   - A trace is valid if ALL constraints are satisfied
   - Violations indicate deviations from expected behavior
   - Can be used for anomaly detection

5. ADVANTAGES:
   - Declarative: Focus on constraints, not sequences
   - Compact: Captures essence without full model
   - Flexible: Allows any sequence satisfying constraints
   - Interpretable: Easy to understand individual rules

6. LIMITATIONS:
   - May not capture all behavioral patterns
   - Requires complete log for accurate constraints
   - Some constraints may be coincidental

7. USE FOR:
   - Compliance checking
   - Process auditing
   - Anomaly detection
   - Understanding mandatory relationships
   - Validating process instances

8. COMPARISON:
   - vs Petri Net: Declarative vs procedural
   - vs DECLARE: Log skeleton is simpler subset
   - vs DFG: Log skeleton captures more than direct follows

REPRESENTATION 10: DECLARE
============================================================

=== DECLARE INTERPRETATION GUIDE ===

DECLARE is a declarative process modeling language based on temporal logic constraints.

1. CORE PHILOSOPHY:
   - "Everything not forbidden is allowed"
   - Specifies constraints that must be satisfied
   - Any execution path respecting constraints is valid
   - Opposite of procedural models (Petri nets, BPMN)

2. CONSTRAINT TEMPLATES:

   EXISTENCE CONSTRAINTS:
   - Existence(A, n): A must occur at least n times
   - Absence(A, n): A can occur at most n-1 times
   - Exactly(A, n): A must occur exactly n times
   - Init(A): A must be the first activity
   - End(A): A must be the last activity

   RELATION CONSTRAINTS:
   - RespondedExistence(A, B): If A occurs, B must also occur (before or after)
   - CoExistence(A, B): A and B always occur together or both absent
   - Response(A, B): If A occurs, B must eventually follow
   - Precedence(A, B): B can only occur if A has occurred before
   - Succession(A, B): Response(A,B) AND Precedence(A,B)

   NEGATIVE CONSTRAINTS:
   - NotCoExistence(A, B): A and B cannot both occur in same trace
   - NotSuccession(A, B): A cannot be followed by B
   - NotChainSuccession(A, B): B cannot immediately follow A

   CHAIN CONSTRAINTS (immediate succession):
   - ChainResponse(A, B): B must immediately follow A
   - ChainPrecedence(A, B): A must immediately precede B
   - ChainSuccession(A, B): Both chain response and precedence

   ALTERNATING CONSTRAINTS:
   - AlternateResponse(A, B): Each A followed by B before next A
   - AlternatePrecedence(A, B): Each B preceded by A after previous B
   - AlternateSuccession(A, B): Both alternate response and precedence

3. READING DECLARE OUTPUT:
   - Template name with involved activities
   - Support: Percentage of traces satisfying constraint
   - Confidence: Strength of the constraint
   - Example: "Response(Submit, Review): support=95%, confidence=0.98"

4. SEMANTICS:
   - Constraints as LTL (Linear Temporal Logic) formulas
   - Trace valid iff all constraints satisfied
   - Empty trace may be valid (if no mandatory constraints)

5. DISCOVERY ALGORITHMS:
   - Mine constraints from event logs
   - Filter by support/confidence thresholds
   - Remove redundant constraints

6. ADVANTAGES:
   - Flexible: Many valid executions
   - Compact: Few rules describe complex behavior
   - Natural for knowledge workers
   - Easy to understand individual constraints

7. LIMITATIONS:
   - Can be hard to understand combined effect of many constraints
   - May allow unintended behavior
   - Checking all constraints can be complex

8. USE FOR:
   - Knowledge-intensive processes
   - Compliance requirements
   - Flexible workflow modeling
   - Process monitoring and alerting
   - Understanding what MUST happen vs what CAN happen

Existence: the activity is executed at least once.

Responded existence: given a couple of activities (A, B), if A occurs then B also occurs.

=== LOG ATTRIBUTES INTERPRETATION GUIDE ===

Log attributes provide statistical metadata about the event log, offering a high-level overview before detailed process mining.

1. PURPOSE:
   - Summarize the event log's characteristics
   - Provide context for interpreting process models
   - Identify data quality issues
   - Understand the scope of the process

2. COMMON ATTRIBUTES:

   CASE-LEVEL STATISTICS:
   - Number of cases: Total process instances
   - Case duration: Min, max, mean, median time from start to end
   - Activities per case: How many events in each trace
   - Variant count: Number of unique execution paths

   EVENT-LEVEL STATISTICS:
   - Total events: Total number of recorded events
   - Event classes: Unique activity types
   - Resources: People/systems performing activities
   - Timestamps: Time range of the log

   ACTIVITY STATISTICS:
   - Activity frequencies: How often each activity occurs
   - Start activities: Which activities begin traces
   - End activities: Which activities end traces
   - Self-loops: Activities that repeat immediately

3. READING THE OUTPUT:
   - Numeric summaries with distributions
   - Lists of unique values for categorical attributes
   - Time-based statistics for temporal analysis
   - Frequency tables for activity occurrence

4. DATA QUALITY INDICATORS:
   - Missing values: Incomplete event records
   - Duplicate events: Potential logging issues
   - Timestamp anomalies: Events out of order
   - Unusual case durations: Outliers or errors

5. EXAMPLE OUTPUT FORMAT:
   ```
   Cases: 1,000
   Events: 15,423
   Activities: 12 unique
   Variants: 87
   Timespan: 2024-01-01 to 2024-12-31
   Mean case duration: 3.5 days
   Most frequent activity: "Process Application" (2,341 occurrences)
   Start activities: ["Submit Request", "Create Case"]
   End activities: ["Close Case", "Archive"]
   ```

6. USE FOR:
   - Initial log exploration
   - Setting expectations for model complexity
   - Identifying filtering needs
   - Communicating process scope to stakeholders
   - Validating log completeness

7. IMPLICATIONS FOR MODELING:
   - High variant count: Complex process, may need filtering
   - Few activities: Simpler models expected
   - Many resources: Consider organizational mining
   - Long durations: Look for bottlenecks

8. COMPARISON WITH OTHER REPRESENTATIONS:
   - Attributes: WHAT is in the log (descriptive)
   - DFG/Petri Net: HOW activities relate (structural)
   - Variants: WHICH paths are taken (behavioral)

9. PREPROCESSING GUIDANCE:
   - Filter infrequent variants for cleaner models
   - Handle missing timestamps appropriately
   - Consider resource/organizational perspective
   - Aggregate similar activities if too granular
