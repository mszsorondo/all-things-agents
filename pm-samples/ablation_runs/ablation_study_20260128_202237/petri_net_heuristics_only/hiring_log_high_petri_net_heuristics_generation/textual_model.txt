AS-IS Process Model

Process overview and purpose
- Purpose: Manage a candidate hiring pipeline from application through screening, interviews, background checks, and, when applicable, issuance of a job offer or rejection.
- Scope captured by the discovered Petri net (Heuristics Miner):

  - Parallelism between checks, rework loops (behavioral interview and offer), and rare reopenings after a rejection.

Key stakeholders and roles involved
- Roles are not explicitly specified in the source model. No swimlane assignments can be made without inventing actors.

Detailed step-by-step process flow
Start conditions and triggers
- Trigger: Candidate submits an application (Hand In Job Application).
- Initial marking: source0 -> Hand In Job Application.

Core activities and control flow
1) Hand In Job Application
   - Normal path: proceeds to Telephonic Screening.
   - Alternate path: immediate rejection without telephonic screening (an observed short-circuit to Application Rejected).

2) Telephonic Screening
   - Decision point:
     - Reject: route directly to Application Rejected.
     - Proceed: enable downstream checks. The model emits tokens that initiate both:

     - Escalate: trigger Extensive Background Check.
     - Reject: route to Application Rejected.

4) Screening Interview (may be in parallel with Background Check)
   - Outcomes:
     - Proceed: enable Coding Interview (via an internal routing step).
     - Escalate: trigger Extensive Background Check.
     - Reject: route to Application Rejected.

5) Extensive Background Check (escalation)
   - Outcomes:
     - Proceed: enable Coding Interview.
     - Reject: route to Application Rejected.

6) Coding Interview
   - Decision point:
     - Reject: route to Application Rejected.
     - Proceed: choose a specialization interview track. The model allows branching to one of:

       - Frontend Interview, or
       - ML Interview.
     - Structural note: The Petri net’s structure (a single pre-place feeding three alternative interview transitions) allows exactly one specialization per firing of Coding Interview; however, because preconditions for Coding Interview can be met multiple times (due to unsynchronized upstream paths), the AS-IS model does not prevent multiple specialization interviews from occurring in the same case.

7) Specialization Interview (one selected path per occurrence)
   - Backend Interview OR Frontend Interview OR ML Interview
   - Outcomes:
     - Proceed: enable Behavioral Interview.
     - Reject: route to Application Rejected.

8) Behavioral Interview
   - Outcomes:
     - Proceed: enable Make Job Offer.
     - Reject: route to Application Rejected.
     - Rework loop: may re-enter Behavioral Interview (model explicitly shows a loop-back, allowing repeated behavioral interviews).

9) Make Job Offer

   - Completion: Case can complete after Make Job Offer (end state).
   - There is no modeled “accept/decline” beyond “Make Job Offer”; the discovered model ends upon offer issuance.

- There is no enforced synchronization before Coding Interview; either Background Check or Screening Interview completion is sufficient to enable the Coding Interview. Extensive Background Check may also be triggered by either check and, if performed, may lead either to rejection or to Coding Interview. Net effect: Coding Interview can begin while the other check is still pending.

Exception handling and error paths
