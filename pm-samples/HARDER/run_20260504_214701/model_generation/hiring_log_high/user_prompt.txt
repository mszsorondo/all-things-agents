REPRESENTATION 1: PROCESS_TREE
============================================================


=== PROCESS TREE INTERPRETATION GUIDE ===

A Process Tree is a hierarchical representation of process behavior.

OUTPUT FORMAT:
--------------
"->( 'Activity A', X( tau, ->( 'Activity B', *( 'Activity C', tau ) ) ), +( 'Activity D', 'Activity E' ) )"

OPERATORS (prefix notation):
- ->(...): SEQUENCE - Execute children left-to-right in order
- X(...): EXCLUSIVE CHOICE - Execute exactly one child
- +(...): PARALLEL - Execute all children concurrently (interleaved)
- *(...): LOOP - First child is body, second is exit condition
- tau: SILENT activity (invisible, used for optional/skip paths)

READING THE OUTPUT:
- Operators are written as: OPERATOR( child1, child2, ... )
- Activity names are in single quotes: 'Activity Name'
- tau (without quotes) represents silent/skip transitions
- Nesting shows hierarchical structure

EXAMPLE INTERPRETATIONS:
- ->( 'A', 'B', 'C' ): Do A, then B, then C (sequence)
- X( 'A', 'B' ): Do either A or B (exclusive choice)
- +( 'A', 'B' ): Do A and B in parallel (any interleaving)
- *( 'A', tau ): Repeat A zero or more times (loop with silent exit)
- X( tau, 'A' ): Optionally do A (can skip)
- ->( 'A', X( tau, 'B' ), 'C' ): Do A, optionally B, then C

COMPLEX EXAMPLE:
"->( 'Start', X( tau, *( 'Review', tau ) ), +( 'Approve', 'Notify' ), 'End' )"
Means: Start, then optionally review (repeatable), then approve AND notify in parallel, then End

INDUCTIVE MINER PROPERTIES:
- Always produces sound (properly completing) models
- May introduce tau for fitness to observed behavior
- Block-structured (properly nested, no arbitrary jumps)

REPRESENTATION 2: DFG
============================================================


=== DIRECTLY-FOLLOWS GRAPH (DFG) INTERPRETATION GUIDE ===

A DFG shows the frequency of direct succession between activities.

OUTPUT FORMAT:
--------------
"If I have a process with flow:

Activity A -> Activity B ( frequency = 1234  performance = 82439.794 )
Activity B -> Activity C ( frequency = 567  performance = 81906.421 )
Activity C -> Activity D ( frequency = 345  performance = 0.000 )
..."

READING THE OUTPUT:
- Each line: "Source -> Target ( frequency = N  performance = T )"
- frequency: Number of times this direct succession was observed
- performance: Average time between activities (in seconds, 0.000 if instant)
- Lines are typically sorted by frequency (descending)

INTERPRETATION:
1. HIGH FREQUENCY EDGES (>1000): Main process flow paths
2. MEDIUM FREQUENCY (100-1000): Common alternative paths
3. LOW FREQUENCY (<100): Rare variants or exceptions
4. SELF-LOOPS (A -> A): Activity repetition (rework)
5. PERFORMANCE VALUES:
   - High values: Bottlenecks or waiting times
   - 0.000: Activities happen simultaneously or instantly after

LIMITATIONS:
- Cannot distinguish XOR (exclusive) from AND (parallel) splits
- May show paths that don't complete (A->B doesn't mean B always follows A)
- Sensitive to noise in event logs

USE FOR:
- Quick process overview
- Identifying bottlenecks (high performance values)
- Finding main vs alternative paths
- Detecting loops and rework

REPRESENTATION 3: HEURISTICS_NET

=== HEURISTICS NET INTERPRETATION GUIDE ===

A Heuristics Net improves on DFG by using dependency measures to identify
true causal relationships between activities.

OUTPUT FORMAT:
--------------
"Heuristics Net:

Activities (N): Activity1, Activity2, ...

Start activities: StartActivity1, StartActivity2, ...
End activities: EndActivity1, EndActivity2, ...

Dependency relations (activity -> activity: dependency_value):
  ActivityA -> ActivityB: dependency=0.999, frequency=1234
  ActivityC -> ActivityD: dependency=0.850, frequency=567
  ..."

READING THE OUTPUT:

1. ACTIVITIES: List of all activities in the process

2. START/END ACTIVITIES: Entry and exit points of the process

3. DEPENDENCY RELATIONS:
   - Source -> Target: Causal relationship from source to target
   - dependency: Measure from 0 to 1 (higher = stronger causality)
   - frequency: How many times this succession was observed

DEPENDENCY MEASURE FORMULA:
- dependency(A,B) = (|A>B| - |B>A|) / (|A>B| + |B>A| + 1)
- Range: -1 to +1 (we show only positive, strong dependencies)
- Near 1.0: Very strong causal relationship
- Near 0.5: Moderate relationship
- Below 0.5: Usually filtered out as noise

INTERPRETING DEPENDENCY VALUES:
- 0.9-1.0: Almost always A causes B (main flow)
- 0.7-0.9: Strong relationship (common path)
- 0.5-0.7: Moderate relationship (alternative path)
- <0.5: Weak/coincidental (typically noise)

ADVANTAGES OVER DFG:
- Filters noise using dependency thresholds
- Identifies true causal vs coincidental relationships
- Handles loops of length 1 and 2
- Shows strength of each dependency

USE FOR:
- Understanding main process flow
- Identifying strong vs weak paths
- Filtering out noise in event logs
- Process analysis before formal modeling

REPRESENTATION 4: PETRI_NET_INDUCTIVE
============================================================


=== PETRI NET INTERPRETATION GUIDE ===

A Petri net is a mathematical model for distributed systems.

OUTPUT FORMAT:
--------------
"If I have a Petri net:

places: [ p_1, p_2, p_3, ..., sink, source ]
transitions: [ (id1, 'Activity Name'), (id2, 'Activity Name'), (skip_1, None), ... ]
arcs: [ source->(Activity, 'Activity'), (Activity, 'Activity')->p_1, ... ]

initial marking: ['source:1']
final marking: ['sink:1']"

READING THE OUTPUT:
- places: List of place names (p_N for internal, source/sink for start/end)
- transitions: Tuples of (internal_id, 'Label') where None = silent transition
- arcs: Connections as source->target (both directions Place↔Transition)
- initial/final marking: Token distribution at start/end

PETRI NET CONCEPTS:

1. PLACES (circles): Represent states or conditions in the process
   - Initial marking: Places with tokens at the start (process entry points)
   - Final marking: Places with tokens at the end (process exit points)
   - Empty places: Intermediate states

2. TRANSITIONS (rectangles): Represent activities or events
   - Labeled transitions: Visible activities (e.g., "Submit Application")
   - Silent/tau transitions: Internal logic without visible activity
   - Parallel transitions: Can fire simultaneously (concurrent activities)

3. ARCS (arrows): Connect places and transitions
   - Place→Transition: Precondition (transition needs token in place to fire)
   - Transition→Place: Postcondition (transition produces token in place)
   - Arc weight: Number of tokens consumed/produced

4. BEHAVIORAL SEMANTICS:
   - A transition is ENABLED when all input places contain tokens
   - Firing consumes tokens from input places, produces in output places
   - Multiple tokens in a place indicate multiple process instances
   - Deadlocks occur when no transition can fire
   - Loops indicate repetitive behavior

5. INDUCTIVE MINER SPECIFICS:
   - Guarantees sound workflow nets (proper completion)
   - May introduce silent transitions for control flow
   - Handles noise and incomplete behavior in logs

REPRESENTATION 5: PETRI_NET_HEURISTICS
============================================================


=== PETRI NET (HEURISTICS MINER) INTERPRETATION GUIDE ===

The Heuristics Miner produces Petri nets using frequency-based dependency measures,
making it more robust to noise than Alpha Miner.

OUTPUT FORMAT:
--------------
The output follows this structure:
"If I have a Petri net:

places: [ intplace_Activity, pre_Activity, splace_in_A_B_0, ... ]
transitions: [ (Activity, 'Activity'), ... ]
arcs: [ source->target, ... ]

initial marking: ['source0:1']
final marking: ['sink0:1']"

PLACE NAMING CONVENTIONS:
- intplace_X: Internal place for activity X
- pre_X: Pre-condition place for activity X
- splace_in_A_B_N: Split place connecting A to B (N is index)
- source0, sink0: Start and end places

DEPENDENCY MEASURE:
- Calculated as: (|A>B| - |B>A|) / (|A>B| + |B>A| + 1)
- Range: -1 to +1
- Values close to 1: Strong causal dependency A->B
- Values close to 0: No clear dependency
- Used with thresholds to filter noise

ADVANTAGES:
- Handles noisy event logs
- Detects loops of length 1 and 2
- Identifies long-distance dependencies
- Produces cleaner models than Alpha miner

READING THE OUTPUT:
- More places than Alpha miner (intermediary routing places)
- All visible activities become transitions
- Complex routing structures for varied behavior
- Split places (splace) indicate choice or parallel patterns

WHEN TO USE:
- Real-world event logs with noise
- When Alpha miner produces poor results
- Complex processes with loops
- When you need to filter infrequent behavior

# === ABSTRACT VARIANTS INTERPRETATION GUIDE (pm4py.llm) ===

## WHAT THIS OUTPUT REPRESENTS

This output describes the **distinct execution paths (process variants)** observed in an event log.
Each variant corresponds to a unique ordered sequence of activities executed by cases in the process.

The variants shown are the **most frequent ones**, listed in descending order of frequency, and truncated if needed to respect the maximum output length (`max_len`).

---

## OUTPUT FORMAT (TYPICAL)

```
If I have a process with the following process variants:

 Activity A -> Activity B -> Activity C -> Activity D ( frequency = 32.5%  performance = 319390.265 )
 Activity A -> Activity B -> Activity E ( frequency = 28.1%  performance = 146345.624 )
 Activity A -> Activity F -> Activity G -> Activity H ( frequency = 21.4%  performance = 229938.161 )
 ...
```

The initial sentence may be present if `response_header=True`.

---

## HOW TO READ EACH LINE

Each line has the form:

```
Activity1 -> Activity2 -> ... -> ActivityN ( frequency = F  performance = P )
```

Meaning:

• `Activity1 -> Activity2 -> ... -> ActivityN`
= the exact ordered sequence of activities executed in that variant (control-flow path)

• `frequency = F`
= the **relative frequency** (proportion or percentage of cases) that follow this exact path
(because `relative_frequency=True`)

• `performance = P`
= the **aggregated case duration** (throughput time) of cases that follow this variant
computed using the selected aggregation method
(default: mean of case durations)

Units depend on the timestamp resolution in the log (e.g., seconds, minutes, milliseconds).

If a secondary aggregation is configured, performance may appear as:

```
performance = P (secondary = Q)
```

---

## IMPORTANT BEHAVIORAL DETAILS

• Variants are sorted by decreasing frequency
• Only the most frequent variants fitting within `max_len` are shown
• Rare variants may be omitted
• Performance refers to **whole-case duration**, not individual activity durations
• Performance is computed only if `include_performance=True`
• Frequencies are **relative proportions**, not absolute counts
• Header text may be present if `response_header=True`

---

## INTERPRETATION PRINCIPLES

### 1. CONTROL-FLOW ANALYSIS

* Variants with the highest frequency represent the dominant execution paths (“happy paths”)
* Shared prefixes across variants indicate where the process diverges
* Unusual or rare paths indicate exceptions or deviations

### 2. FREQUENCY ANALYSIS

Using relative frequency:

* High frequency variants (e.g., >20%) → core process behavior
* Medium frequency (5–20%) → common alternatives
* Low frequency (<5%) → edge cases or exceptional behavior

These thresholds are heuristic and should be interpreted relative to the domain.

### 3. PERFORMANCE ANALYSIS

* Compare performance values across variants
* Higher performance value = longer average case duration
* Variants with both:

  * high frequency
  * high performance
    are prime candidates for optimization

### 4. STRUCTURAL COMPLEXITY

* More activities in a variant generally imply higher structural complexity
* Long variants with high performance may indicate rework or loops
* Short variants with low performance often represent fast completion paths

---

## WHAT THIS OUTPUT IS SUITABLE FOR

This abstraction is designed for **human or LLM reasoning**, not for direct machine parsing.

It is suitable for:

• Identifying main vs alternative process paths
• Explaining process behavior in natural language
• Detecting deviations or exceptional flows
• Comparing efficiency of different execution paths
• Summarizing complex event logs
• Serving as structured input for LLM-based process analysis

---

## WHAT THIS OUTPUT IS NOT

• It is not a complete list of all variants (due to truncation)
• It is not a formal process model (Petri net, BPMN)
• It is not a structured dataset
• It does not include resource, data, or organizational perspectives
• It does not show intra-activity waiting times

---

## SUMMARY

This output encodes:

```
Variant = (Activity Sequence, Relative Frequency, Aggregated Case Duration)
```

Serialized as natural language for LLM-based interpretation.

=== PETRI NET (ILP MINER) INTERPRETATION GUIDE ===

The ILP (Integer Linear Programming) Miner constructs Petri nets that perfectly

--------------

"If I have a Petri net:

- 'source' and 'sink' for start/end
- Minimized number of places (optimization objective)

SPECIAL TRANSITIONS:
- (■, None) or similar: Silent/tau transitions for routing
- Visible activities: (ActivityName, 'ActivityName')

KEY CHARACTERISTICS:
- Perfect fitness: ALL observed traces can replay
- Minimal structure: Fewest places/arcs that explain behavior
- May include silent transitions for complex routing
- Numerically named places (optimization result)

OPTIMIZATION OBJECTIVE:
- Minimize structural complexity
- Subject to: All traces must be replayable
- Token flow conservation at each step

ADVANTAGES:
- Guaranteed perfect fitness
- Mathematically rigorous
- No heuristic parameters to tune
- Finds minimal explaining structure

LIMITATIONS:
- Computationally expensive for large logs
- May overfit to observed behavior
- Does not handle noise well
- Scalability issues with many activities

WHEN TO USE:
- Small to medium-sized logs
- When perfect fitness is required
- Clean logs without noise
- Understanding exact behavioral boundaries
