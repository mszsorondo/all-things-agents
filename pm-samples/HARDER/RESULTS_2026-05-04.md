# HARDER Benchmark — Multi-perturbation Trace Classification

**Date**: 2026-05-04
**Script**: `phase5_benchmark_harder.py`
**Generator LLM**: `openai:gpt-5`
**Validator LLM**: `gpt-5-mini`
**Sample size**: 100 valid + 50 invalid per perturbation type (10 types) per dataset
**Datasets**: hiring, hospital, lending, renting (4 total)

## Motivation

The original `phase5_benchmark.py` evaluates the textual AS-IS model with a **single** perturbation type (`random_swap_events`, A1) and reports one F1 per dataset using a balanced 100v + 100i sample. This gives one number but tells us nothing about *which kinds* of process violations the validator catches.

`phase5_benchmark_harder.py` extends the benchmark to **10 distinct log-based perturbation types**, each evaluated on 50 invalid traces drawn by perturbing seeds from the same 100-trace valid pool. The textual-model generation pipeline is unchanged (same 3 representations as the original, plus a separate run with a curated 5-rep set).

The result is a per-perturbation breakdown that surfaces the validator's strengths and blind spots, plus comparison metrics designed to be unbiased across configurations.

## Metric Choices

We deliberately **do not** report a single "aggregate F1" computed by pooling all 500 invalids against the 100 valids. That metric is biased by the 1:5 valid/invalid ratio (precision is artificially capped at 0.167 in the worst case vs 0.500 in the original 1:1 benchmark) and is not directly comparable across configurations or to the original phase5 numbers.

We use two complementary metrics:

1. **Macro F1** — mean of per-type F1 values. Each perturbation type computes F1 against its own 50 invalids + the shared 100 valids, then we average across types. Each perturbation contributes equally; the per-type ratio is held constant across configurations so comparisons are fair.

2. **Total FP count** (or equivalently, **FP rate over total invalids**) — pure error count, no ratio assumption. Lower = better. Comparable directly across configurations because the underlying invalid pool size is identical (10 types × 50).

For per-type breakdowns we report **TN rate (specificity)** — the fraction of invalids of that type correctly classified as INVALID. This is unbiased and the natural per-type quantity (it is `1 − FP_rate_for_that_type`).

**Recall is exactly 1.000 in every configuration and every dataset**: the validator never rejects a valid trace. All variation comes from FPs.

## Methodology

### Pipeline

```
XES log → discover N representations
        → gpt-5 generates AS-IS textual model from concatenated representations
        → sample 100 valid traces from log
        → for each of 10 perturbation types:
             apply perturbation to seeds drawn from the 100 valid traces
             reject perturbed traces whose activity sequence still appears as a real
               variant in the log (variant lookup)
             collect 50 effectively-invalid traces per type
        → gpt-5-mini classifies all 600 traces as VALID/INVALID
        → compute per-type F1, TN rate, and total FP count
```

### Perturbation taxonomy (10 log-based types)

| ID  | Name                                | Mechanism                                                                    |
|-----|-------------------------------------|-------------------------------------------------------------------------------|
| A1  | random_swap                         | swap two events at random positions                                           |
| A3  | dependency_aware_swap               | swap a pair (a,b) where `always_before(a, b)` holds in the log                |
| B1  | insert_out_of_alphabet              | insert an activity not in the log alphabet                                    |
| B2  | insert_misplaced_existing           | insert an existing activity at a random position                              |
| B3  | insert_duplicate_unique             | duplicate an activity that always appears once per trace                      |
| C1  | delete_mandatory                    | delete an activity present in 100% of traces                                  |
| C2  | delete_start_or_end                 | delete the first or last event                                                |
| D1  | cross_role                          | reassign an event to a resource that never performs that activity             |
| E1  | two_swaps                           | apply A1 twice                                                                |
| E2  | swap_and_insert                     | apply A1 + (B1 or B2)                                                         |

All except D1 are validated by **variant lookup**: the perturbed activity sequence must NOT appear as any observed trace variant in the log. D1 is invalid by construction (changes resources, not activities).

### Representation sets compared

Two configurations were tested with identical perturbations, traces, and validator settings:

**Config A — "3-rep" (matches `phase5_benchmark.py` defaults)**
- `PETRI_NET_INDUCTIVE`
- `DFG`
- `ABSTRACT_VARIANTS`

**Config B — "5-cur" (curated set chosen for diversity, minimal redundancy)**
- `PROCESS_TREE` — best single-rep mean F1 (0.976 in the single-rep ablation study), hierarchical with explicit operators
- `DFG` — local activity-to-activity transitions with frequencies
- `ABSTRACT_VARIANTS` — enumerated trace sequences observed in the log
- `DECLARE` — temporal logic constraints (`Existence`, `Exactly 1`, `Always Before`, `Response`, `Never Together`, ...)
- `LOG_ATTRIBUTES` — global attribute statistics including resource lists

The 5-rep set was chosen by inspecting `representation_interpretation_guides/` and the leave-one-out and single-rep results in `ablation_results/` and `ablation_runs/`. Petri Net variants other than Inductive were dropped as redundant; Heuristics Net was dropped as subsumed by DFG; Log Skeleton was dropped as a strict subset of DECLARE.

### Sample size justification

Sample sizes follow the empirical curve in the thesis (Table C.5):
- n=50 per type gives F1 std ≈ 0.04 — adequate for per-type ranking
- The macro-F1 (mean of 10 types) effectively averages 10 such estimates, std ≈ 0.013
- The original benchmark used 100 valid + 100 invalid, std ≈ 0.02 → comparable precision

## Findings

### 1. Worst-performing perturbation: D1 (cross-role) by a large margin

D1 is the **only perturbation where the validator fails 100% of the time, in every dataset, in both representation configurations**. Across the two runs combined, 0 out of 400 cross-role perturbations were detected (200 per config × 2 configs).

| Rank | Perturbation              | TN rate (3-rep) | TN rate (5-cur) | Macro F1 (3-rep) | Macro F1 (5-cur) |
|------|---------------------------|-----------------|-----------------|------------------|------------------|
| 🔴 1 | **D1 cross_role**         | **0.000**       | **0.000**       | **0.800**        | **0.800**        |
| 🟡 2 | C2 delete_start_or_end    | 0.770           | 0.675           | 0.949            | 0.928            |
| 🟢 3 | B1 insert_out_of_alphabet | 0.865           | 0.930           | 0.968            | 0.983            |
| 🟢 4 | B2 insert_misplaced       | 0.870           | 0.925           | 0.969            | 0.982            |
| 🟢 5 | B3 insert_duplicate_unique| 0.880           | 0.940           | 0.971            | 0.986            |

D1's macro F1 of 0.800 is a **mathematical floor**: it occurs exactly when TN=0 and FP=50 with TP=100, FN=0:

    P = 100 / (100 + 50) = 0.667
    R = 100 / 100 = 1.000
    F1 = 2·P·R / (P+R) = 2·0.667 / 1.667 = 0.800

Any perturbation that the validator **never** detects produces exactly this F1. D1 hits this floor in all 8 (dataset × config) combinations.

This is a **structural limitation** of the representation choice, not a tunable parameter. The 3-rep set (PETRI_NET_INDUCTIVE, DFG, ABSTRACT_VARIANTS) is pure control-flow and contains zero resource information. The 5-cur set adds LOG_ATTRIBUTES which lists resources globally, but does not contain resource→activity bindings. Without a representation like `pm4py.discover_handover_of_work_network` or a manual resource→activity mapping computed from the log, no choice from the existing pm4py representations can fix D1.

The textual model generated by gpt-5 is honest about this: *"The event log does not reliably map each activity to one responsible role; the names suggest likely involvement, but the assignments are not explicit in the source."*

C2 (delete start/end) is the **second-worst**, and the only perturbation that gets *worse* with the curated representation set (0.770 → 0.675). The 5-cur set's DECLARE constraints and Process Tree's tau/silent operators may give the validator interpretive license to tolerate missing boundary events as alternative valid paths.

### 2. Order violations (swaps) are caught reliably in both configs

Macro F1 ≥ 0.99 for A1, A3, E1, E2 in both configurations. The textual AS-IS model carries enough sequencing information for the validator to detect:
- Random swaps (A1)
- Swaps that break a strict `always_before` dependency (A3)
- Two simultaneous swaps (E1)
- Combined swap + insert (E2)

### 3. The 3-rep vs 5-cur trade-off

The two sets perform **equivalently overall** (macro F1 = 0.963 in both, FP rates 17.1% vs 17.5%) but with different per-type profiles:

| The 5-cur set is better at... | The 3-rep set is better at... |
|---|---|
| B1 insert OOA (+6.5% TN rate)        | A1 random_swap (-2.5%)        |
| B2 insert misplaced (+5.5%)          | A3 dependency swap (-4.0%)    |
| B3 insert duplicate unique (+6.0%)   | C1 delete mandatory (-4.5%)   |
|                                      | **C2 delete start/end (-9.5%)** |

Hypothesis: DECLARE constraints (`Existence`, `Exactly 1`) and LOG_ATTRIBUTES (explicit activity list) help the validator notice unexpected/extra activities (insertions). On the other hand, the same DECLARE constraints may give the validator interpretive license that *softens* judgement about deletes (any subset of the constrained behavior can look like an alternative valid path through `tau`/silent transitions in process trees and X-choice operators in DECLARE).

### 4. Per-dataset variability dominates per-set differences

The 5-cur set varies by ±0.10 macro-F1 across datasets (0.939 hiring, 0.980 lending). The mean difference between configurations is 0.001. **Dataset structure interacts more strongly with representation choice than the choice itself.**

### 5. Hiring is consistently the hardest dataset

Across both configurations, hiring has the lowest macro F1 (0.947, 0.939) and the highest FP count (121, 139). It has the most variants per case (386), the most parallel/optional paths, and only 1 mandatory activity — properties that make individual perturbations look more like alternative valid paths.

## Limitations

1. **Single LLM pair.** Results are for `gpt-5` (generator) + `gpt-5-mini` (validator). Different validator models would change per-type weaknesses.
2. **B2 ambiguity.** Inserting an existing activity at a random position can occasionally yield a sequence that *coincidentally* matches an unobserved-but-valid path. The variant-lookup filter rejects perturbations that match observed variants, but a stronger oracle (token replay against the discovered Petri net) would catch even rarer near-duplicates.
3. **D1 floor.** F1 = 0.800 for D1 is a hard floor: any configuration that fully fails on D1 gets exactly this F1. To distinguish *how badly* the validator fails, per-trace error analysis is needed.

## Future work

- **Add resource-aware representations**: include `pm4py.discover_handover_of_work_network` or a custom activity→resources table, then re-run only D1 against the new configuration. This is the only path to actually reducing D1 FPs.
- **Discovery-based perturbations not yet tested**:
  - **A2 concurrency-aware swap**: swap only between activities that are NOT in parallel branches of a Process Tree.
  - **C3 delete critical decision point**: identify gateway-following activities from a BPMN/Petri net and delete them.
- **Validator strength**: re-run with `gpt-5` as validator; the prompt-side limit may dominate per-type weakness.
- **Per-trace D1 error analysis**: which (activity, fake-resource) pairs fool the validator most often? Could reveal what kind of resource info would help most.

## Baseline comparison

Two non-APM baselines were evaluated on the **same trace set** as APM-5cur to isolate
what the LLM agent actually contributes. Both are documented at:

- **Baseline A — classical conformance**: `baselines/RESULTS.md` and `baselines/classical_runs/run_20260505_004920/summary.md`
- **Baseline B 5cur — pm4py.llm raw context, no agent**: `baselines/RESULTS.md` and `baselines/pm4pyllm_runs/run_20260505_083600_5cur/`

Full breakdown is in `baselines/RESULTS.md`. Five-line per-baseline summary:

### Baseline A (classical conformance, no LLM at validation) → APM loses

DFG footprints and Petri Net Inductive + alignments beat APM-5cur macro F1 across all 4 datasets (0.978 and 0.974 vs APM 0.963), with 39% fewer FPs (213 vs 350) and zero LLM cost. Classical equals or beats APM on **every** perturbation type **except** D1 cross_role, where both score 0/50 (same control-flow blind spot). C2 delete-start/end is the only type where APM is much worse than classical (TN-rate 0.675 vs 0.815).

**Largest deltas (mean across 4 datasets, classical DFG-footprints minus APM-5cur)**:
+0.140 in C2 delete_start_or_end, +0.095 in C1 delete_mandatory, +0.070 in B1 insert_OOA. APM never wins on any perturbation against the best classical pair.

### Baseline B 5cur (raw pm4py.llm abstractions as system prompt, gpt-5-mini validator) → APM wins on macro F1, loses on D1

Macro F1 is much lower than APM (mean **0.738** over 4 datasets vs APM's 0.963) because raw context makes the validator **reject 25-48% of valid traces** — recall collapses from 1.000 (APM) to 0.52-0.75 (B 5cur). But on detection alone (TN rate, ignoring valid losses), **B 5cur catches D1 cross_role 34.5% of the time on average across 4 datasets vs APM's 0%**. The raw `pm4py.llm.abstract_log_attributes` output preserves per-pair (resource, activity) literal data that the agent's narrative rewrite smoothes out.

**Largest per-type TN-rate deltas (B 5cur minus APM-5cur, mean of 4 datasets)**:
**D1 cross_role +0.345, C1 +0.095, C2 +0.080, B1 +0.010** (B wins);
B3 -0.145, A1 -0.060, B2 -0.050 (APM wins). One-line interpretive: **the agent doesn't add detection capability, it adds tolerance.**

### Combined implication for the thesis

The LLM-agent textual model (APM) is **dominated** by classical conformance for control-flow violations and **surpassed by raw pm4py.llm dump** on the one perturbation that requires preserving non-control-flow literal data (D1). Where APM does win is on the trade-off axis: it produces the most balanced precision/recall combination — never rejecting valid traces (recall=1.000) while still catching most invalids. If recall is the priority, APM is best; if total error count or D1 detection is the priority, classical or raw-LLM beat APM respectively.
